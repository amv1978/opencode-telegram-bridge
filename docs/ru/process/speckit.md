# Speckit: изменения по спецификации

Любое изменение начинается с короткой спецификации. Процесс намеренно
минимальный: три файла, без бюрократии.

## Правило

**Никакого кода без спецификации.** Фича или пакет исправлений — это:

1. **spec** — цель, критерии приёмки, что вне рамок;
2. **plan** — технический подход, файлы, риски;
3. **tasks** — упорядоченные шаги, включая тесты;
4. код + тесты (сначала чистые helper'ы, затем адаптеры);
5. ручная проверка в **Telegram и Discord**;
6. release gate: `bunx tsc --noEmit` + `bun test` + проверка установщика.

## Где лежат спецификации

```
specs/
  _template/{spec.md,plan.md,tasks.md}   # шаблон в репозитории
  <версия>-<slug>/{spec.md,plan.md,tasks.md}  # локально, в .gitignore
```

`specs/*` добавлен в `.gitignore`: рабочие спецификации остаются на машине.
Версионируется только шаблон, чтобы формат был общим. Копирование:

```powershell
Copy-Item specs\_template specs\0.9.0-my-feature -Recurse
```

## Минимальная спецификация

- **Цель** — что меняется для пользователя, одно-два предложения.
- **Критерии приёмки** — наблюдаемое поведение, чекбокс на пункт.
- **Вне рамок** — что трогать нельзя.

План — только модули и поток данных; задачи — настолько мелкие, чтобы
закрываться за один заход. Тесты — в списке задач, а не «потом».

## Матрица ручных проверок

| Поверхность | Минимум |
|---|---|
| Telegram | личный чат, тема форума, `/status`, typing во время длинного хода |
| Discord | тред или канал, `/status`, typing во время длинного хода |
| Порядок | prompt из Desktop/TUI с вложением появляется раньше ответа |

## Release gate

```bash
bunx tsc --noEmit
bun test
# установщик: ISCC installer\ocbridge.iss (и ocbridge-lite.iss)
```

Затем тихая локальная установка и `GET http://127.0.0.1:7788/api/state` должны
показать новую версию и работающий Telegram. Только после этого — CHANGELOG,
версия, коммит/тег (публикация — отдельное явное решение).
